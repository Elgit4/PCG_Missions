# CMI backend implementation status

**Baseline:** CMI Follow-up v2.1  
**Workspace:** `supabase-cmi/` (isolated from historical `supabase/`)  
**Status:** Identity, contacts/follow-up and restricted-pastoral schemas validated on an isolated local CMI Supabase stack through GitHub Actions. Domain SQL remains in review drafts pending final schema approval and permanent migration promotion.

## Implemented in this slice

- Dedicated Supabase CLI project with configuration at `supabase-cmi/supabase/config.toml`, a distinct local project ID and non-conflicting ports.
- Church and branch foundation with branch-aware candidate keys.
- Supabase Auth-linked staff profile; no PIN/password storage.
- Exactly six CMI role catalogue entries.
- Capability catalogue and explicit role-capability join structure; no grants seeded.
- Time-bounded staff role assignments supporting multiple roles.
- Teams, memberships, service areas and staff area coverage.
- RLS enabled and browser grants withheld on all foundation tables.
- Initial pgTAP structural and deny-by-default test file at `supabase-cmi/supabase/tests/identity_authorization_foundation.test.sql`.
- Contacts/follow-up domain SQL draft covering nine tables, integrity constraints, indexes, idempotent capture metadata, and conservative assignment rules.
- Matching pgTAP draft covering table presence, RLS, closed Data API grants, shared-phone handling, branch consistency, capture idempotency and assignment constraints.
- Restricted-pastoral SQL draft with prayer requests, intercessor assignments, care groups/records/assignments/interactions, and dedicated append-only prayer/care access-audit ledgers.
- Matching 20-assertion pgTAP draft covering RLS denial, no direct policies, assignment constraints, branch isolation, oversight reasons and immutable audit rows.
- CMI CI now generates temporary migration filenames using `supabase migration new`, copies both domain drafts into the local workspace, runs all pgTAP suites, and cleans up the temporary files from the GitHub runner.

## Deliberately not implemented yet

- Staff email + PIN credential activation/exchange/reset endpoints. The credential lifecycle and Supabase Auth integration require approval.
- Role capability grants and role/record scope policies. R-01–R-12 and D-01 remain pending.
- Permanent, approved contacts/follow-up migration files. The current SQL was copied into a temporary filename generated by `supabase migration new`, applied successfully in CI and then removed from the runner; source remains under `schema-drafts/`.
- Permanent, approved prayer/care migration and audited narrative-read Edge Function/RPC. The current SQL was applied as a temporary CLI-generated migration in CI; no direct browser read path or mediated read endpoint is implemented.
- Event registration, transport capacity, check-in and public endpoints.
- Public content publication.
- SMS provider adapter, send pipeline, callbacks or automation.
- Offline queue and device enrollment.
- Production deployment or hosted database linking.

## Blocking design reconciliation

See [schema reconciliation crosswalk](../docs/16_CMI_SCHEMA_RECONCILIATION_AND_DECISION_CROSSWALK.md). Event/public-content schema work can proceed as review drafts, but permanent migrations and access policies remain gated by the applicable ERD reconciliations and stakeholder decisions.

## Verification

**Valid local-CI validation:** [GitHub Actions run 42436473154](https://github.com/Elgit4/PCG_Missions/actions/runs/42436473154) used Supabase CLI 3.0.0 and the dedicated `supabase-cmi/supabase/` project. It generated temporary migration filenames with `supabase migration new`, applied the CMI identity foundation plus contacts/follow-up and restricted-pastoral SQL drafts, then ran three pgTAP suites: identity/authorization (14 assertions), contacts/follow-up (24 assertions), and restricted pastoral (20 assertions). Logs report each suite `ok`, `All tests successful`, `Result: PASS`; the local stack stopped successfully. Temporary domain migrations and tests were removed from the GitHub runner during cleanup and were not committed as permanent migrations.

This proves the current SQL drafts parse and apply against the isolated local Supabase/PostgreSQL stack, and the structural/deny-by-default tests pass. It does **not** prove full six-role RLS authorization, because role-capability grants and client policies remain intentionally absent. The trusted contact-merge operation, audited prayer/care read endpoints, authentication flow, event/public endpoints and actual integration tests remain unimplemented. No hosted Supabase project was accessed, linked, migrated or modified; no real visitor/prayer data or live SMS was used.
